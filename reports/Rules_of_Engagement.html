Isolated Cybersecurity Practice & Security Testing Agreement

Governing Law Compliance US CFAA (18 U.S.C. § 1030) / UK Computer Misuse Act Effective Date November 12, 2026

1. Purpose and Objectives

The purpose of this document is to establish a rigorous, legally compliant, and technically sound operational framework for conducting application security assessments, penetration testing practice, and vulnerability research. This document serves as the governing agreement defining the boundaries of authorized activity.

  • Provide hands-on training in application security using standard industry methodologies (OWASP Top 10).
  • Ensure that all practice remains 100% contained within a dedicated, isolated virtualization sandbox.
  • Instill a professional code of ethics and legal accountability prior to performing any vulnerability assessment.

2. Authorized Testing Environment & 3. Target Application

Security testing is authorized exclusively on the local containerized environment described below:

  • Host Workstation: Student Personal Local Machine.
  • Virtualization Platform: Docker / Docker Desktop via Bridge Network Driver.
  • Target Application: OWASP Juice Shop (Docker Image: bkimminich/juice-shop).
  • Application Technology: Node.js (Express), SQLite database, Angular SPA.

4. Target URL & Network Endpoint

MANDATORY TARGET URL: http://localhost:3000  |  http://127.0.0.1:3000
HOST SOCKET BINDING: 127.0.0.1:3000 (TCP)
Under no circumstance shall testing be targeted at an external domain name, public IP, or LAN address.

5. Scope of Authorization

In-Scope (Strictly Authorized) Out-of-Scope (Strictly Prohibited)

8. Network Restrictions

1. Strict Loopback: The target must remain bound exclusively to 127.0.0.1. Wildcard 0.0.0.0 is forbidden.
2. No Port Forwarding: Home router NAT forwarding, UPnP, or DMZ hosting must never be enabled for port 3000.
3. No Public Bridging: The container must not be bridged directly to a public or wireless network interface.

9. Data Handling Requirements

1. Synthetic Data Only: All accounts, credentials, and transactions used during testing must be synthetic/mock data.
2. Artifact Sanitization: All screenshots and reports prepared for academic submission must be sanitized to remove private host paths, real user credentials, or API keys.
3. Ephemeral Storage: Upon conclusion of the academic evaluation, all temporary container data should be cleanly removed.

10. Mandatory Stop Conditions

STOP TESTING IMMEDIATELY IF:
  1. Any tool or payload establishes an outbound connection to an external or unfamiliar IP address.
  2. The container port becomes accessible from another machine on the LAN or the Internet.
  3. Host system experiences extreme CPU/RAM degradation, thermal throttling, or OS instability.
  4. You discover any real-world personal identifying information (PII) or production keys.
  5. Any uncertainty arises regarding whether an action falls within the authorized scope.

11. Incident Response & Containment Procedure

STEP 1 (CONTAIN): Immediately run docker stop juice-shop.
STEP 2 (ISOLATE): Disconnect host from local network (disable Wi-Fi / unplug Ethernet).
STEP 3 (LOG): Preserve container logs: docker logs juice-shop > containment-log.txt.
STEP 4 (ESCALATE): Notify the academic instructor/advisor in writing within 2 hours.
STEP 5 (PURGE): Execute docker rm -f juice-shop and await written re-authorization.
